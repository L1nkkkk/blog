如果你学过 OpenGL

OpenGL 和 Vulkan 驱动的是同一块 GPU，要做的事情一样多。区别在于谁来做：OpenGL 的驱动替你管理命令缓冲、同步、资源状态和窗口缓冲，Vulkan 把这些全部交还给你。所以本教材的每个概念在 OpenGL 里几乎都有对应物，只是多数藏在驱动里。每章有一个黄色标记的对比表，帮你把新概念挂到已有的认识上。

02命令先录下来，之后才执行

vkCmd* 开头的函数都不会让 GPU 立刻干活，它们只是往 command buffer 里写一条记录。写完后把整个 buffer 提交给 queue，GPU 在之后某个时刻按顺序执行。思路和 Unity 的 CommandBuffer、UE 的 RHICommandList 相同，区别是 Vulkan 要你自己管这块 buffer 的状态。

录几条命令，end，然后 submit，看 GPU 怎么逐条执行。执行期间试着点 reset 或 begin。

图里唯一不由你的代码触发的箭头是 GPU 执行完成。它发生在另一条时间线上，CPU 这边不会自动知道。

Command pool

command buffer 从 command pool 里分配。pool 管理底层内存，有三条规则值得记住：

  • 一个 pool 绑定一个 queue family，从它分配的 buffer 只能提交到这个族的 queue。
  • pool 不是线程安全的。多线程录制时每个线程用自己的 pool。
  • 可以 reset 单个 buffer，也可以 reset 整个 pool，后者一次清空它名下所有 buffer。两种都要求相关 buffer 不在 Pending。

begin 时还可以带 ONE_TIME_SUBMIT 标志，告诉驱动这次录的内容只提交一次。带了这个标志的 buffer 执行完后进入 Invalid 状态，必须 reset 才能再用。

03CPU 和 GPU 是两条时间线

vkQueueSubmit2 立刻返回，它只是把工作放进队列。CPU 录一帧通常比 GPU 画一帧快。下面的模型里 CPU 不停地录制并提交，中间没有任何等待。点“运行”，再把 GPU 耗时调大。

积压只是表面现象。真正先出事的是第 2 章那件事：CPU 回头想复用一个 command buffer 时，它还在 Pending。所以 CPU 必须在某些点上等 GPU，GPU 上的某些工作之间也必须排出先后。Vulkan 为这两种等待各给了一个工具。

一次 submit 能带什么

VkSubmitInfo2 有三个列表：开始前要 wait 的 semaphore、要执行的 command buffer、完成后要 signal 的 semaphore。每个 wait 的 semaphore 还带一个 stage mask，表示命令执行到哪个阶段才需要等它。vkQueueSubmit2 另外接受一个 fence 参数。

再记三个 API 事实，编排留给你：

  • vkAcquireNextImageKHR 可以带一个 semaphore 或 fence，image 真正可用时才 signal。函数返回编号时 image 不一定已经可用。
  • vkQueuePresentKHR 可以指定若干 semaphore，等它们 signal 后才呈现。
  • vkDeviceWaitIdle 会阻塞到这个 device 上所有 queue 的工作都执行完。它简单可靠，代价是整个程序停顿，不适合每帧调用。

Vulkan 1.2 起还有 timeline semaphore，Task 01 用不到，知道存在即可。

06Pipeline barrier：给 GPU 上的访问排先后

第 3 章的 fence 和 semaphore 管的是“一次提交”和“另一次提交”之间的先后。但在同一个 command buffer 内部，命令之间也有先后问题，这归 pipeline barrier 管。

名字里的 pipeline 指的是：每条命令在 GPU 上要流过若干阶段（stage）。一次 draw 依次经过顶点输入、顶点着色器、片元着色器、颜色附件输出等阶段；一次 compute dispatch 只有 compute shader 一个阶段；一次拷贝属于 transfer 阶段。你录制命令的顺序是确定的，但 GPU 为了效率会让相邻命令重叠执行：前一条还在后面的阶段，后一条已经进入前面的阶段。如果两条命令碰了同一块资源，结果就取决于时序。

barrier 是录在两条命令之间的一条声明：它之前的命令在某些阶段做的某些访问，必须先于它之后的命令在某些阶段做的某些访问。

内存依赖srcAccessMask → dstAccessMasksrc 阶段里这种访问写下的数据，要对 dst 阶段里那种访问可见。约束的是数据：GPU 有缓存，执行完不等于写到了后续阶段能看到的地方
layout 转换oldLayout → newLayout仅 image。转换发生在 src 访问之后、dst 访问之前。转换本身算一次对 image 的读写

stage 和 access 必须配对才有意义：access 说的是“在这个 stage 里做的哪一种访问”。只写 stage 不写 access，等于只排了时间，没保证数据可见。access 填了某个 stage 根本做不出来的访问类型，validation 会报错。

作用范围和调用形式

  • barrier 只在同一个 queue 内有效。src 一侧覆盖这条 barrier 之前提交到该 queue 的命令，dst 一侧覆盖它之后的命令，不限于同一个 command buffer。
  • 跨 queue 或者和呈现引擎之间的先后，barrier 管不了，要靠 semaphore。
  • vkCmdPipelineBarrier2 接受一个 VkDependencyInfo，里面有三个数组：全局的 memory barrier、针对 buffer 的、针对 image 的。只有 image barrier 带 layout 字段。
  • barrier 不能录在 vkCmdBeginRendering 和 vkCmdEndRendering 之间（少数特殊情况除外，Task 01 遇不到）。

旧版的 vkCmdPipelineBarrier 把 stage 作为整条命令的参数，access 放在每个 barrier 结构体里。Vulkan Tutorial 用的是旧版。synchronization2 把 stage 和 access 放到了同一个结构体里，语义没变。

07窗口尺寸、像素尺寸与 swapchain extent

swapchain 的尺寸在创建时固定。窗口变了，旧 swapchain 就和 surface 对不上了，需要重建。这里有三个容易混的数：窗口坐标尺寸、实际像素尺寸、surface 报告的 extent。

VulkanContext::rebuild_swapchain 已经处理了尺寸判断和重建本身。它的头文件注释写了一条前置条件，那一条由你的帧循环负责满足。你会从三个渠道得知需要重建：SDL3 的 SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED 事件、acquire 的返回值、present 的返回值。三者到达的时机不同，不能只依赖其中一个。

和 OpenGL 对比

VulkanOpenGL 里对应什么关键差别
重建 swapchain不需要。default framebuffer 自动变大变小这是 Vulkan 多出来的工作
更新 viewport 和 scissorglViewport两边都要做，且都要用像素尺寸
窗口坐标与像素尺寸的区别相同，SDL_GetWindowSizeInPixels 同样适用这是窗口系统的问题，与图形 API 无关
最小化时 extent 为 0，不能创建 swapchain通常照常渲染也不会出错Vulkan 需要你显式跳过
你自己创建的离屏附件你自己创建的 FBO 纹理两边都要自己按新尺寸重建

读报错的顺序：先看 VUID 对应的规范原句，它说的是哪条规则被违反；再看对象句柄，确定是哪个对象；最后回到自己的代码找调用点。本仓库的约定是，求助之前先用一句话复述这条报错的含义。
